# ESP32-P4 小智智能家居中控国赛优化计划方案

更新时间：2026-05-24  
项目路径：`E:\MCU\esp32\p4\xiaozhi-for-p4`  
目标赛事：全国大学生嵌入式芯片与系统设计竞赛芯片应用赛道，乐鑫科技赛题方向

## 1. 项目定位

当前项目已经形成一个有竞争力的雏形：ESP32-P4 作为高性能中控屏，ESP32-S3 从机作为楼层控制节点，小智作为语音与 LLM 入口，LVGL 作为本地 HMI，MQTT 作为主从链路。

建议把最终作品定位为：

> 基于 ESP32-P4 + ESP32-S3 多节点协同的 AIoT 智慧安全家庭中控系统

核心卖点不是“能控制灯”，而是：

- 本地触控、语音大模型、自动化规则三种控制入口统一到同一套设备模型。
- 主机和多从机之间有可验证的 MQTT 闭环控制、ACK、心跳和掉线恢复。
- 传感器数据真实采集，形成安全告警、环境监测、趋势记录和自动决策。
- LVGL 面板不是简单页面，而是面向评委演示的实时可视化中控台。
- 具备火灾、水浸、异常离线等安全场景，能马上弹窗、唤醒、播报、联动设备。
- 具备可复现实验工具，包括 MQTT 模拟脚本、日志回放、压力测试和现场兜底方案。

乐鑫 2026 赛题官方说明中，ESP32-P4/ESP32-S3 是指定平台；官方鼓励边缘 AI、高性能图形人机交互、无线通信和智能交互 AIoT 方向。当前项目同时覆盖这些方向，路线是正确的。后续重点应从“功能堆叠”转为“可靠闭环 + 真实数据 + 可展示创新”。

参考：

- 乐鑫 2026 嵌赛页：https://www.espressif.com/zh-hans/ecosystem/education/competition/socchina

## 2. 当前能力评估

### 2.1 已具备的基础

- ESP32-P4 Function EV Board 主机已接入 LVGL 智能家居面板。
- 小智聊天能力、LLM 控制入口和 MCP 工具已有基本雏形。
- LVGL 总览、控制、网络、设置页面已经可运行。
- MQTT 主从协议已经从单向控制推进到 V2 心跳、ACK、设备模型同步。
- 三个楼层从机已经能分别编译，具备真实设备控制与传感器上报基础。
- 火灾告警已经接入 LVGL 弹窗、小智唤醒和警告提示音。
- 已新增 `tools/mqtt_iot_simulator.py`，可在没有实物从机时模拟三层楼控制器。
- 编译已统一使用项目根目录下唯一 `build` 目录，避免多 build 目录污染。

### 2.2 当前主要短板

- ESP-Hosted 无线链路偶发无法连接，仍是系统级风险。一旦网络不可用，小智和 MQTT 都会失效。
- BOOT 引脚唤醒小智的链路还没有形成稳定的“按键事件 -> 应用事件 -> UI/语音状态”闭环。
- MQTT 当前已经有 ACK 和心跳，但还缺少序列号、事务状态、重试、超时回滚和错误可视化。
- 传感器真实数据还需要标定，尤其火焰、烟雾、雨滴等模拟量阈值。
- 从机代码仍按楼层复制，后续维护成本高，容易出现一楼修了、二楼三楼漏修的问题。
- LVGL 页面已有视觉雏形，但还缺少“答辩级”的状态解释、趋势图、事件时间线和一键演示模式。
- 小智角色更换尚未资产化，仍需要表情状态表、资源转换、内存评估和默认回退策略。
- 现场演示缺少“可控脚本 + 录屏素材 + 故障兜底”的完整链路。

## 3. 必须优先修复的问题

### P0-1：ESP-Hosted 网络稳定性

问题风险：主机无法联网会导致 MQTT、LLM、小智服务全部不可用，是比赛现场最危险的问题。

建议修复方向：

- 把 ESP-Hosted 初始化、连接、断开、重连状态做成明确状态机：`INIT -> WAIT_SLAVE -> NETIF_UP -> WIFI_CONNECTING -> WIFI_READY -> MQTT_READY`。
- 在 LVGL 网络页显示 ESP-Hosted 当前阶段、最近错误码、重连次数、IP、RSSI、MQTT 状态。
- 对 `E (35076) transport: Not able to connect with ESP-Hosted slave device` 这类错误增加指数退避重试和手动重连按钮。
- 增加启动自检：检测 C6/C5 slave 是否响应、hosted transport 是否 ready、Wi-Fi 是否拿到 IP。
- 增加现场兜底：如果 hosted 失败，LVGL 仍能进入离线演示模式，使用模拟数据展示 UI 和控制闭环。

验收标准：

- 冷启动连续 20 次，网络成功率不低于 95%。
- Wi-Fi 热点断开再恢复，60 秒内自动恢复 MQTT。
- LVGL 能明确显示“等待无线协处理器 / Wi-Fi 连接中 / MQTT 已连接 / MQTT 失败”。

### P0-2：BOOT 引脚唤醒小智

问题风险：如果按键唤醒不可靠，语音交互入口会显得不完整。

建议修复方向：

- 先确认当前板子 BOOT 键实际 GPIO。ESP32-P4 Function EV Board 常见 BOOT 键接到 P4 的 strapping/BOOT 相关 GPIO，不能直接猜，需要按板级 BSP 或原理图核对。
- 不建议直接把 BOOT 当普通功能键长期占用，优先复用项目已有按键抽象层。
- 若 BOOT 只能在上电/下载模式中使用，建议外接独立唤醒键或使用触摸屏上的唤醒按钮。
- 软件链路应统一为：按键 ISR 或轮询 -> `Application::WakeWordInvoke()` 或等价事件 -> 小智 UI 切到聆听态 -> 音频提示。
- LVGL 设置页增加“按键测试”区域，按下后显示最近一次按键时间和触发动作。

验收标准：

- 单击 BOOT 或独立唤醒键可稳定唤醒小智。
- 连续按 50 次无崩溃、无重复触发风暴。
- 睡眠/待机状态下按键行为与屏幕状态一致。

### P0-3：MQTT 控制闭环可靠化

问题风险：现在已能控制和同步，但比赛级作品必须能证明“命令确实被执行”，而不是 UI 乐观更新。

建议协议增强：

- 在命令包中加入 `seq` 或 `transaction_id`，主机发送命令时记录待确认事务。
- ACK 返回原命令、设备 ID、GPIO index、执行值、结果码、seq。
- 心跳继续作为状态权威来源，ACK 只证明“收到并执行过命令”。
- 主机 UI 控制设备时进入 `pending` 状态，ACK 或心跳确认后再变为最终状态。
- 超时未确认时显示“执行超时”，并允许重试。
- MQTT QoS 建议：控制命令 QoS 1，心跳 QoS 0，告警 QoS 1，普通传感器 QoS 0。
- 增加 retained birth/will 或在线状态 topic，让主机能更快判断从机上下线。

建议状态机：

```text
用户/LLM 发起控制
  -> 主机生成 seq
  -> MQTT 发布命令
  -> LVGL 显示 pending
  -> 从机执行
  -> 从机回复 ACK
  -> 从机立即补发心跳
  -> 主机 ACK 匹配 seq
  -> 主机以心跳状态刷新模型
  -> LVGL/MCP/小智状态同步
```

验收标准：

- 模拟脚本和三套真实从机都支持 seq/ACK。
- 断网、从机掉线、ACK 丢包时 UI 能显示明确失败状态。
- LLM 查询状态时返回的是设备模型真实状态，而不是最后一次发送命令。

### P0-4：传感器真实化与标定

问题风险：评委会关注是否是真实采集，不能只靠模拟值。

建议修复方向：

- 每个传感器建立统一数据结构：原始 ADC、滤波值、工程单位、状态等级、更新时间、有效标志。
- 烟雾、火焰、雨滴至少做滑动平均或中值滤波，避免一跳就误报。
- 每个阈值写入 NVS 或配置文件，LVGL 设置页支持现场调节。
- 火灾判断不要只依赖单个传感器。建议用火焰 + 烟雾双条件，或单传感器高阈值立即告警、低阈值预警。
- 心跳包必须包含所有原始值和状态值，便于答辩解释。

建议数据等级：

```text
0 = 正常
1 = 预警
2 = 告警
3 = 传感器故障或离线
```

验收标准：

- LVGL 可显示 ADC 原始值、状态、阈值和最近更新时间。
- 火灾模拟可通过真实传感器触发，也可通过脚本触发。
- 告警解除只解除 UI 弹窗，不伪造传感器恢复；传感器恢复后才允许下一次告警。

## 4. 架构优化方向

### 4.1 主机软件架构

建议把主机分为五层：

```text
Application / Xiaozhi
  小智状态机、LLM、MCP 工具、语音播报

Smart Home Service
  MQTT 客户端、命令事务、规则引擎、告警中心

Device Model
  设备状态、传感器状态、楼层状态、系统状态

LVGL HMI
  总览页、控制页、网络页、设置页、告警弹窗、趋势图

Board / BSP
  ESP-Hosted、Wi-Fi、音频、屏幕、触摸、TF 卡、按键
```

约束：

- LVGL 只能读模型和发事件，不直接拼 MQTT topic。
- MQTT 只能更新模型，不直接操作 LVGL 控件。
- LLM/MCP 只能调用 Smart Home Service，不直接改 UI。
- 告警中心统一处理火灾、水浸、离线、求助等事件。

### 4.2 从机代码架构

当前三个从机按楼层复制，短期能跑，长期不适合比赛冲刺。

建议重构为：

```text
slave_common/
  app_mqtt.c
  app_protocol.c
  app_heartbeat.c
  app_control.c
  app_sensor.c
  app_config.h

xiaozhi_slave_Firstfloor/
  floor_config.h

xiaozhi_slave_Secondfloor/
  floor_config.h

xiaozhi_slave_Thirdfloor/
  floor_config.h
```

每层只保留差异：

- 设备名、楼层 ID。
- GPIO 映射。
- 传感器类型和阈值。
- 设备数量。

验收标准：

- 修改 MQTT 协议只改一处 common 代码。
- 三个从机构建命令不变，产物仍在根目录 `build/slave_first`、`build/slave_second`、`build/slave_third`。

### 4.3 事件与告警中心

建议增加 `smart_home_event_center`：

- 输入：MQTT 心跳、ACK、传感器变化、按键、LLM 命令、LVGL 点击。
- 输出：设备模型更新、LVGL 事件、小智播报、日志记录、自动化联动。

核心事件：

- `DEVICE_ONLINE`
- `DEVICE_OFFLINE`
- `COMMAND_ACK`
- `COMMAND_TIMEOUT`
- `SENSOR_WARNING`
- `FIRE_ALARM`
- `RAIN_ALARM`
- `HELP_ALARM`
- `RULE_TRIGGERED`
- `NETWORK_RECOVERED`

这样后续加水浸、人体存在、门磁、功耗都不会破坏原有逻辑。

## 5. 建议新增硬件与传感器

### 5.1 优先级最高

- SHT40 / SHT31 / AHT20：温湿度，稳定、便宜、适合总览页。
- BH1750：光照，用于自动调光和“人来灯亮”的逻辑。
- MQ-2 / MQ-135 或更可靠烟雾模块：厨房/火灾场景。
- 火焰传感器：与烟雾组合判断火灾。
- 雨滴 / 水浸传感器：阳台、卫生间、水管漏水场景。
- 门磁：一楼大门/窗户状态，便于安全演示。
- 人体存在传感器：PIR 可先用，升级可用 LD2410 毫米波。

### 5.2 用于拉开差距

- SCD40 / SCD41：CO2，体现健康环境监测。
- PMS5003 / PMSA003：PM2.5，体现空气质量。
- HLW8012 / BL0937 / PZEM：用电功耗统计，体现节能控制。
- 摄像头：人脸识别、火焰图像辅助判断、远程查看。
- 蜂鸣器 / 声光报警模块：让火灾告警不只停留在屏幕。
- 机械执行器模型：窗帘、天窗、晾衣架、排风扇、消防喷淋模拟。

### 5.3 不建议盲目堆叠

- 不建议一次性加入太多低质量模拟模块，会让布线、供电、误报变复杂。
- 不建议把天气 API 当核心能力。天气适合做辅助展示，本地真实传感器才是主体。
- 不建议把所有传感器都接在同一个从机上，应按楼层场景分布。

## 6. LVGL 面板优化方向

### 6.1 总览页

总览页应该让评委 5 秒内看懂系统价值。

建议显示：

- 三个楼层控制器在线状态、最近心跳时间。
- MQTT 状态、消息数、最近消息延迟。
- 火灾、水浸、求助、离线等安全状态。
- 环境状态：温度、湿度、CO2、PM2.5、光照。
- 设备状态：灯、窗、门、晾衣架、排风扇。
- 今日事件数、今日告警数、自动化触发次数。

建议新增：

- 楼层拓扑图：用一张简化房屋剖面图表示 1F/2F/3F。
- 事件时间线：最近 10 条事件，比如“3F 火警预警”“2F 雨滴传感器触发”“1F 门已打开”。
- 告警优先级条：红色火灾最高，黄色水浸/离线其次。

### 6.2 控制页

建议从“按钮列表”升级为“设备卡片 + 状态反馈”：

- 每个设备卡片显示：名称、楼层、在线、当前状态、pending/失败状态。
- 舵机类设备使用滑条或角度控件，不只开关。
- 灯光类设备可扩展亮度滑条。
- 控制失败时卡片边框变红并显示“超时”。
- LLM 控制和触摸控制的结果在同一张卡片上同步。

### 6.3 网络页

网络页要服务现场排障：

- ESP-Hosted 状态。
- Wi-Fi SSID、RSSI、IP。
- MQTT broker、连接状态、重连次数、最近错误。
- 三套从机最近心跳时间。
- 一键 Discover、一键重连 MQTT、一键进入模拟模式。

### 6.4 设置页

建议加入比赛现场有用的设置：

- 传感器阈值校准。
- 设备映射检查。
- 按键测试。
- 音量/播报开关。
- 角色皮肤选择。
- 清空日志。
- 导出演示日志到 TF 卡。

### 6.5 视觉与品牌

当前蓝色丝印已经接近赛题口号，但后续建议：

- 使用正式 PNG/SVG 资源替代代码绘制，避免字体差异。
- 保持“9th / AI for Design & Design for AI”在首屏可见。
- 自定义小智角色应该形成完整状态集：待机、聆听、思考、说话、成功、错误、告警。
- 所有页面统一字体、间距、圆角、颜色和图标风格。

## 7. LLM 与小智能力优化方向

### 7.1 控制能力

当前 MCP 工具已经能控制设备，建议升级为更自然的语义控制：

- “打开二楼客厅灯”
- “把三楼天窗打开一半”
- “关闭所有灯”
- “现在家里安全吗”
- “为什么三楼报警”
- “帮我进入离家模式”

LLM 工具层必须返回结构化结果：

- 命令已发送。
- 是否收到 ACK。
- 最终设备状态。
- 如果失败，失败原因是 MQTT 未连接、从机离线、设备不存在还是执行超时。

### 7.2 场景模式

建议新增场景：

- 回家模式：玄关灯开、客厅灯开、解除布防。
- 离家模式：关闭灯、关闭窗、开启安防。
- 睡眠模式：关闭公共区域灯、保留夜灯、降低音量。
- 雨天模式：关闭天窗、收回晾衣架。
- 火灾模式：弹窗、播报、打开排风或关闭相关电源、记录事件。
- 演示模式：按固定脚本依次展示控制、传感器、告警、语音。

### 7.3 本地兜底播报

当前火灾告警是警告音 + 唤醒小智。为了现场稳定，建议增加本地 OGG 语音资源：

- “检测到三楼发生火灾，请立即检查现场。”
- “检测到二楼雨滴传感器触发，已关闭天窗。”
- “主控与二楼控制器连接中断。”

本地播报不依赖云端，即使网络不稳定也能展示安全能力。

## 8. 边缘 AI 与创新功能建议

### 8.1 推荐主创新点

建议选择一个主创新点深做，不要平均用力。

首选方向：

> 多模态安全感知 + AI 语义中控

实现方式：

- 传感器层：烟雾、火焰、雨滴、水浸、人体存在、门磁。
- AI 层：小智理解自然语言，结合实时状态解释风险。
- HMI 层：LVGL 用告警弹窗、事件时间线和楼层图展示风险。
- 控制层：自动执行联动，比如雨天关窗、火警断电/开排风/播报。

这样既符合智能家居，又符合边缘 AI、HMI、AIoT。

### 8.2 可选加分功能

- Wi-Fi CSI 人体存在检测：乐鑫官方生态中有相关方向，创新性强，但调试难度较高。
- 摄像头火焰/人员检测：P4 有 MIPI-CSI 和算力优势，但模型部署、帧率、内存压力较大。
- 本地异常检测：用最近一段传感器数据判断异常，不完全依赖阈值。
- 能耗优化：根据人体存在和光照自动关灯，统计节能百分比。
- OTA 升级：主机和从机可远程升级，体现工程完整性。

建议路线：

- 国奖冲刺建议至少做“传感器融合 + 场景联动 + 可解释 LLM 查询”。
- 如果时间充足，再加 Wi-Fi CSI 或摄像头作为亮点。

## 9. 数据记录与可验证性

比赛作品要能“证明自己真的工作过”。

建议利用 TF 卡记录：

- MQTT 收发摘要。
- 从机上线/掉线记录。
- 命令事务记录。
- 传感器历史数据。
- 告警事件。
- 用户触摸/语音控制事件。

建议文件：

```text
/sdcard/smart_home/events_YYYYMMDD.jsonl
/sdcard/smart_home/sensors_YYYYMMDD.csv
/sdcard/smart_home/mqtt_YYYYMMDD.log
/sdcard/smart_home/config.json
```

LVGL 可新增“日志页”或在设置页中显示最近事件。

验收标准：

- 断电重启后能保留最近配置。
- 现场演示结束能导出一份事件日志。
- 答辩时可以展示“火警触发 -> 弹窗 -> 播报 -> 联动”的时间顺序。

## 10. 测试体系

### 10.1 自动化脚本

现有 `tools/mqtt_iot_simulator.py` 应继续扩展为正式测试工具。

建议新增模式：

- `--scenario fire`：火灾演示。
- `--scenario rain`：下雨收衣/关窗演示。
- `--scenario offline`：从机掉线恢复。
- `--scenario stress`：高频心跳和控制压力测试。
- `--record`：记录主机响应。
- `--replay`：回放历史 MQTT 流量。

### 10.2 实物测试

每轮固件修改后至少验证：

- 主项目编译。
- 三套从机编译。
- 模拟脚本 self-test。
- 主机连接 broker。
- 三套从机上线。
- 每个设备可控。
- 每个传感器可显示真实数据。
- 火警弹窗和解除按钮正常。
- 小智唤醒和播报正常。

### 10.3 现场演示兜底

必须准备三层兜底：

- 第一层：真实从机 + 真实传感器。
- 第二层：真实主机 + MQTT 模拟脚本。
- 第三层：主机离线演示模式，直接使用本地模拟模型。

这样即使现场网络或从机出问题，也能完整展示 UI 和交互逻辑。

## 11. 工程质量与可靠性

### 11.1 FreeRTOS 与任务

建议检查：

- LVGL 访问是否全部在 LVGL 锁或 LVGL 线程内完成。
- MQTT 回调是否只更新模型，不直接操作 UI。
- 音频、小智、MQTT、LVGL 是否存在优先级反转。
- 所有任务栈余量是否记录。
- 是否启用 TWDT 监控关键任务。

### 11.2 内存

建议在总览或设置页显示：

- free heap。
- largest free block。
- PSRAM free。
- LVGL 内存使用。
- 资源加载失败次数。

主项目 app 分区剩余空间已不算很宽裕，后续加角色动画、语音资源、摄像头模型时必须重新评估分区。

### 11.3 安全

建议：

- MQTT broker、端口、用户名密码从配置读取，不硬编码在代码中。
- 演示 broker 和正式 broker 分离。
- 现场可以无密码，但文档中要说明生产版本支持鉴权。
- 危险命令如全开、全关、火灾解除要有日志。

## 12. 小智卡通角色替换计划

难度评估：中等。

最稳方案：

- 保持现有情绪 key 不变。
- 每个情绪提供同尺寸透明 PNG/GIF/WebP。
- 先做静态帧或轻量 GIF，暂不做 Live2D。
- 加一个角色资源 manifest，避免代码里硬编码每张图。

需要改动：

- `main/assets.cc`：资源声明与默认资源版本。
- `main/display/lvgl_display/emoji_collection.*`：表情集合加载。
- `main/display/lcd_display.cc`：小智状态到表情的映射。
- 资源转换脚本：把图片转成 LVGL 可用资源或打包进文件系统。
- 设置页：增加角色选择和资源加载失败回退。

推荐角色状态：

- idle：待机。
- listen：聆听。
- think：思考。
- speak：说话。
- happy：执行成功。
- error：执行失败。
- alarm：火灾/安全告警。
- sleep：休眠。

验收标准：

- 全部状态切换无黑屏、无明显卡顿。
- 内存占用可控。
- 资源缺失时回退默认角色。

## 14. 建议的最终答辩故事

不要按“我做了几个页面、几个按钮”介绍。建议按真实问题讲：

1. 家庭安全和能源管理需要低延迟、本地可控、可解释的中控系统。
2. 我们用 ESP32-P4 做高性能 HMI 和本地决策，用 ESP32-S3 做楼层节点。
3. 主从通过 MQTT 形成可验证闭环，每个命令都有 ACK、心跳和状态回写。
4. 小智大模型让用户能用自然语言控制和询问系统状态。
5. LVGL 面板提供实时拓扑、告警、趋势和控制反馈。
6. 火灾/雨天/离家等场景能自动联动，并且有本地播报和日志留痕。
7. 系统提供模拟器、日志和压力测试，确保可复现和可工程化。

这条故事线能同时体现：

- 乐鑫芯片平台使用深度。
- 嵌入式实时性。
- AIoT 创新性。
- HMI 完成度。
- 工程可靠性。
- 作品可演示性。
